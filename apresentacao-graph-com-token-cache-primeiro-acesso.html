1. Visão geral da solução

Antes de entrar nos detalhes, a arquitetura pode ser entendida em quatro responsabilidades principais.

AutenticaçãoMSAL + Redis Token Cache para trabalhar com o contexto delegado do usuário.
Coleta inicialConsulta de e-mails e transcrições na Microsoft Graph e persistência no S3 Stage.
Sincronização contínuaSubscriptions avisam sobre novos e-mails e novas transcrições; para e-mail, a Delta Query busca somente o que mudou.
ManutençãoEventBridge dispara a renovação automática das subscriptions de e-mail e transcrição antes da expiração.
Usuário / CRM→ API Gateway→ Lambda→ MSAL + Redis→ Microsoft Graph→ S3 Stage

Mensagem para abrir a apresentação: o desenho completo foi dividido em fluxos independentes. Assim conseguimos discutir primeiro acesso, operação diária e renovação sem misturar responsabilidades.

2. E-mail — primeiro acesso e carga inicial

Esse fluxo responde à pergunta: “O que acontece quando o usuário utiliza a integração pela primeira vez?”

  1. O usuário autentica no CRM.
  2. O Front envia o access token para o backend.
  3. A Lambda utiliza MSAL para trabalhar com o token delegado.
  4. O Token Cache do MSAL é persistido no Redis.
  5. A Lambda consulta os e-mails na Microsoft Graph.
  6. Realiza paginação quando necessário.
  7. Aplica regras de negócio e monta a resposta.
  8. Salva os e-mails coletados no S3 Stage.
  9. Cria a Subscription para futuras notificações.
  10. Salva subscriptionId e expirationDateTime na base de controle.
Rotas e permissões deste fluxo
PassoRota na Microsoft GraphPermissão delegada
Consulta os e-mails GET /me/messages?$top=&$select=&$orderby=receivedDateTime desc Mail.Read
Realiza paginação segue a URL de @odata.nextLink Mail.Read
Cria a Subscription POST /subscriptions
resource: /me/mailFolders('inbox')/messages		 Mail.Read
Diagrama — primeiro acesso de e-mails
Ponto-chave: a carga inicial acontece uma vez. Depois disso, o fluxo normal passa a ser incremental.

3. Transcrições — carga inicial e notificações

A transcrição também pode utilizar Subscription / Change Notification. Assim, depois da carga inicial, o backend pode ser avisado quando uma nova transcrição estiver disponível.

Carga inicial→ Transcrições existentes→ S3 Stage→ Cria Subscription

3.1 Primeiro acesso / carga inicial

  1. A Lambda solicita ao MSAL um token para a Microsoft Graph.
  2. O MSAL consulta primeiro o Token Cache do usuário no Redis.
  3. Se o cache ainda não existir, executa o OBO com a user assertion recebida do Front e salva o Token Cache resultante no Redis.
  4. Consulta as reuniões do período e recupera as transcrições já disponíveis.
  5. Aplica as regras de negócio e salva as transcrições no S3 Stage.
  6. Cria uma Subscription para users/{userId}/onlineMeetings/getAllTranscripts.
  7. Salva subscriptionId, expirationDateTime, usuário e tipo da subscription na base de controle.
Rotas e permissões deste fluxo
PassoRota na Microsoft GraphPermissão delegada
Consulta as reuniões do período GET /me/events?$filter=start/dateTime ge {inicio} Calendars.Read
Lista as transcrições da reunião GET /users/{userId}/onlineMeetings/{meetingId}/transcripts OnlineMeetingTranscript.Read.All
Baixa o conteúdo da transcrição GET /users/{userId}/onlineMeetings/{meetingId}/transcripts/{id}/content?$format=text/vtt OnlineMeetingTranscript.Read.All
Cria a Subscription POST /subscriptions
resource: users/{userId}/onlineMeetings/getAllTranscripts		 OnlineMeetingTranscript.Read.All

3.2 Nova transcrição disponível

Depois que a Subscription está criada, não é necessário ficar consultando o calendário continuamente para descobrir se uma nova transcrição apareceu.

Transcrição disponível→ Graph Subscription→ Change Notification→ Lambda Transcript→ Busca conteúdo→ S3 Stage
  1. A transcrição fica disponível após a reunião.
  2. A Microsoft Graph envia uma Change Notification para o webhook.
  3. A Lambda identifica a Subscription e o usuário.
  4. Utiliza MSAL + Redis para obter um access token válido.
  5. Consulta o transcript/conteúdo correspondente na Microsoft Graph.
  6. Aplica regras de negócio e salva a nova transcrição no S3 Stage.
Rotas e permissões deste fluxo
PassoRota na Microsoft GraphPermissão delegada
Recebe a Change Notification a Graph chama o webhook exposto no API Gateway nenhuma
Consulta o transcript notificado GET /users/{userId}/onlineMeetings/{meetingId}/transcripts/{id} OnlineMeetingTranscript.Read.All
Baixa o conteúdo da transcrição GET /users/{userId}/onlineMeetings/{meetingId}/transcripts/{id}/content?$format=text/vtt OnlineMeetingTranscript.Read.All
Diagrama — nova transcrição disponível
Ponto-chave: para o recurso users/{userId}/onlineMeetings/getAllTranscripts, a notificação só é enviada se a Subscription já existir antes do início da transcrição. Por isso faz sentido criá-la no onboarding do usuário.
Atenção arquitetural: o endpoint getAllTranscripts/delta para sincronização completa/incremental por organizador usa permissão de aplicação (OnlineMeetingTranscript.Read.All), não delegated. Neste desenho, mantivemos o fluxo principal compatível com a estratégia delegated/OBO: carga inicial pelas reuniões do usuário e Change Notification para novas transcrições.

4. E-mail — sincronização incremental

Esse é o fluxo normal depois do onboarding. A Subscription funciona como aviso; a Delta Query recupera somente as mudanças.

Novo e-mail→ Change Notification→ API Gateway→ Lambda→ Delta Query→ S3 Stage
  1. Um novo e-mail chega na caixa do usuário.
  2. A Microsoft Graph envia uma Change Notification.
  3. A Lambda identifica a Subscription e o usuário.
  4. MSAL + Redis recuperam o contexto necessário para chamar a Graph.
  5. A Lambda executa a Delta Query.
  6. Somente alterações desde a última sincronização são processadas.
  7. Os novos dados são salvos no S3.
  8. O novo deltaLink é atualizado na base de controle.
Rotas e permissões deste fluxo
PassoRota na Microsoft GraphPermissão delegada
Recebe a Change Notification a Graph chama o webhook exposto no API Gateway nenhuma
Executa a Delta Query GET /me/mailFolders/{folderId}/messages/delta Mail.Read
Continua a sincronização segue @odata.nextLink e guarda o @odata.deltaLink final Mail.Read
Diagrama — delta de e-mails
Ponto-chave para explicar: a Subscription não representa uma nova carga completa. Ela apenas sinaliza que existe algo novo; a Delta Query mantém a sincronização eficiente.

5. Renovação automática da Subscription

Esse fluxo responde à pergunta: “Como evitamos que as subscriptions expirem?”

  1. O EventBridge executa periodicamente a Lambda de renovação.
  2. A Lambda consulta a base de Subscription Control.
  3. Filtra subscriptions de e-mail e transcrição próximas da expiração.
  4. Recupera o contexto delegado do usuário via MSAL + Redis.
  5. Renova a Subscription na Microsoft Graph.
  6. Atualiza o novo expirationDateTime.
Rotas e permissões deste fluxo
PassoRota na Microsoft GraphPermissão
Lista as subscriptions ativas GET /subscriptions
opcional — a base de controle já tem os registros		 a do recurso assinado
Renova a Subscription PATCH /subscriptions/{subscriptionId}
body: { "expirationDateTime": "..." }		 a do recurso assinado
Regra conceitual: ExpirationDateTime <= agora + margem de renovação e Status = ACTIVE.
Diagrama — renovação de subscription
Ponto-chave: o mesmo processo de renovação pode controlar subscriptions de e-mail e transcrição, diferenciadas por SubscriptionType/Resource.

Como funciona o Token Cache no primeiro acesso

Primeiro acesso: o Redis ainda pode não possuir cache para aquele usuário. O backend carrega o cache persistido do Redis para o MSAL; se não existir, o MSAL executa o OBO com a user assertion recebida na requisição. Depois que o token é adquirido, o estado do Token Cache é serializado e persistido no Redis para as próximas execuções.
Lambda→ MSAL→ Consulta Redis→ Cache existe?→ Sim: usa/renova silenciosamente Não: OBO→ Entra ID→ Persiste Token Cache no Redis

Estrutura sugerida no S3 Stage

Um objeto por item, particionado por usuário e por data de ingestão. O mesmo padrão vale para os dois fluxos.

E-mails
crm-email-stage/
└── usuario-8f3a1c2e-4b7d-4c1a-9f22-7e5d3a1b6c04/   ← objectId do Entra, não o e-mail
    └── 2026/                                        ← data de ingestão
        └── 08/
            └── 16/
                ├── AAA123.json                        ← id da mensagem
                ├── BBB456.json
                └── CCC789.json
Transcrições
crm-transcript-stage/
└── usuario-8f3a1c2e-4b7d-4c1a-9f22-7e5d3a1b6c04/
    └── 2026/
        └── 08/
            └── 16/
                └── MSo1N2Y5ZGFjYy03MWJm/            ← meetingId
                    ├── MSMjMCMjZDAwYWU3.json           ← transcriptId
                    └── MSMjMCMjZDAwYWU3.vtt            ← conteúdo bruto
Por que o id como nome do arquivo: a Microsoft Graph pode reentregar a mesma Change Notification. Como a chave no S3 é derivada do id da mensagem/transcrição, a reentrega sobrescreve o mesmo objeto em vez de duplicar — a gravação fica idempotente sem controle adicional.
Por que data de ingestão e não receivedDateTime: a Delta Query também devolve alterações em itens antigos (um e-mail marcado como lido, por exemplo). Particionando por receivedDateTime, essa alteração gravaria numa partição do passado e quem processa “a pasta de hoje” não a veria. O receivedDateTime continua disponível como campo dentro do JSON.
Ordem sugerida na reunião: Visão geral → primeiro acesso de e-mails → delta de e-mails → transcrições (carga inicial + notification) → renovação. Isso mantém a narrativa principal de e-mail contínua e deixa transcrições como um fluxo relacionado, mas independente.
